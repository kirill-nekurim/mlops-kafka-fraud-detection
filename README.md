# Мониторинг потокового антифрода

Развитие ДЗ3: Kafka → CatBoost → Kafka → PostgreSQL, переобучение в Airflow и
горячая смена модели. Добавлены Prometheus, Grafana, Node Exporter и непрерывный
генератор транзакций. Качество модели здесь не оценивается; графики показывают
реальные обработанные сообщения и записанные результаты.

## Запуск

Нужны Docker и Docker Compose v2. Для полного стека выделите Docker 4–6 ГБ памяти,
особенно если одновременно работают другие проекты. Порты вынесены в `.env.example`.

```bash
git clone https://github.com/kirill-nekurim/mlops-kafka-fraud-detection.git
cd mlops-kafka-fraud-detection
git checkout hw5-monitoring
docker compose up --build -d
```

При лимите Docker около 3 ГБ памяти может не хватать при переобучении.
Для снижения нагрузки можно запустить поток, Airflow и мониторинг без двух
дополнительных интерфейсов:

```bash
docker compose up --build -d airflow fraud_detector db_writer simulator prometheus grafana node-exporter
```

Если полный стек уже запущен, сначала остановите только его интерфейсы:
`docker compose stop kafka-ui interface`. Другие compose-проекты команда не затрагивает.

Первый запуск скачивает образы и зависимости. Проверка состояния:

```bash
docker compose ps -a
docker compose logs --tail 30 fraud_detector db_writer simulator
```

`kafka-setup` и `data_loader` должны завершиться с кодом 0, остальные сервисы работают.
Генератор начинает поток сам, примерно 5 транзакций в секунду. Он сэмплирует реальные
строки `data/train.csv`, создаёт новые UUID и время отправки. Исходное время операции
остаётся признаком модели; мониторинг использует настоящее время скоринга `scored_at`.

Адреса:

- Grafana: http://localhost:3000 — `admin` / `admin`.
- Prometheus: http://localhost:9090; Status → Targets — три `UP`.
- Метрики скоринга: http://localhost:18000/metrics.
- Метрики записи: http://localhost:18001/metrics.
- Airflow: http://localhost:8085 — `admin` / `admin`.
- Kafka UI: http://localhost:8095.
- Streamlit: http://localhost:8505.
- PostgreSQL: localhost:5435, база `fraud`, `postgres` / `postgres`.

Пароли учебные и заданы в compose. Внешние порты мониторинга привязаны к localhost.
Grafana использует отдельного `grafana_reader`: он может только читать `scores`.
Источники данных, дашборды и алерты загружаются через provisioning при старте.
Настраивать их вручную не нужно.

Остановка с сохранением данных:

```bash
docker compose down
```

Не используйте `down -v` для обычной остановки: он удаляет результаты, состояние
Airflow и историю Prometheus. Каталог опубликованных моделей смонтирован отдельно.

## Три дашборда

Откройте в Grafana папку **Fraud Monitoring**:

1. **01 Скоринг и бизнес-показатели** — общий TPS, p95 времени обработки,
   доля флагов фрода, heatmap скоров, время без успешной обработки и загрузки моделей.
   Здесь же PostgreSQL-панели по версиям, фильтруемый TPS, плотность скоров,
   доля фрода по категориям и сумма подозрительных операций во времени.
2. **02 Запись результатов** — скорость успешных INSERT, p95 времени записи,
   число флагов фрода, распределение скоров, задержка скор → БД, ошибки и повторы.
3. **03 Ресурсы Docker Linux VM** — CPU, память, входящая/исходящая сеть,
   занятое место и дисковый I/O. На macOS Node Exporter работает в Linux-среде
   Docker Desktop: это не мониторинг всех процессов macOS.

Дашборды созданы для этого проекта, JSON и конфигурация Prometheus не скопированы
из семинара. Сбор метрик — раз в секунду, обновление Grafana — раз в две секунды.
Для p95 и долей используется окно 30 секунд: сразу после запуска подождите 30–60 секунд.

### Фильтры штата и мерчанта

В первом дашборде переменные **Штат** и **Мерчант** поддерживают несколько значений
и All. Они применяются к PostgreSQL-панелям. Технические Prometheus-панели показывают
весь поток; отдельные временные ряды на каждого мерчанта не создаются.

Для конкретной выборки снимите галочку **All**, выберите штат и закройте список
клавишей Escape. Затем так же выберите мерчанта: его список зависит от штата.
Если в последних 1000 операциях нет выбранного сочетания, график категорий покажет
No data — расширение временного диапазона этого графика не меняет.

- **TPS по выбранным штату и мерчанту**: число успешных скоров в пятисекундном
  интервале, делённое на 5. Время — `scored_at`, а не дата исторической CSV-строки.
- **Плотность скоров**: 20 интервалов шириной 0.05. Высота — доля наблюдений,
  делённая на ширину; сумма площадей столбцов равна 1.
- **Доля фрода по категориям**: сначала выбираются последние 1000 записанных
  операций всего потока, затем применяются фильтры. При меньшем числе строк берутся все.
  Этот график намеренно показывает последний батч, а не выбранный диапазон времени.
- **Сумма подозрительных операций**: сумма `amount` там, где `fraud_flag=1`,
  по времени и выбранным фильтрам. Это дополнительный бизнес-график: он показывает
  денежный объём операций для проверки, а не доказанный финансовый ущерб.

Все доли на графиках — проценты 0–100, модельный score — вероятность 0–1.
`fraud_flag` — предсказание модели, не истинная метка из train.

## Метрики

Скоринг (`fraud_detector:8000`):

- `scorer_transactions_total` — число скоров, подтверждённых выходным Kafka-топиком.
- `scorer_processing_seconds` — histogram полного пути: препроцессинг, inference,
  подтверждение Kafka. Панель p95 строится по бакетам.
- `scorer_score` — histogram вероятностей, бакеты от 0 до 1.
- `scorer_fraud_total` — число флагов фрода; `rate(fraud)/rate(total)` даёт долю
  за последние 30 секунд, нулевой поток защищён от деления на 0.
- `scorer_fraud_ratio` — доля флагов с начала работы процесса, 0–1.
- `scorer_last_success_timestamp_seconds` — время последней успешной обработки.
- `scorer_model_loads_total{model_version}` — успешные загрузки конкретной версии.
- `scorer_model_active{model_version}` — 1 у активной версии, 0 у прежних.
- `scorer_model_loaded_timestamp_seconds{model_version}` — момент успешной загрузки.
- `scorer_errors_total`, `scorer_publish_failures_total`, `scorer_model_load_failures_total`
  — ошибки входных сообщений, публикации и загрузки модели.

Запись (`db_writer:8001`):

- `writer_scores_total`, `writer_fraud_total`, `writer_score` — новые строки,
  флаги и histogram действительно записанных скоров.
- `writer_insert_seconds` — histogram времени INSERT с подтверждением PostgreSQL.
- `writer_delivery_delay_seconds` — histogram времени от вычисления скора до БД.
  **Дополнительная метрика, которой нет в семинаре.** Смотреть p95 в дашборде записи:
  рост показывает отставание потребителя даже при быстром одиночном INSERT.
- `writer_duplicates_total` — повторные transaction_id, которые не добавлены в БД.
- `writer_errors_total`, `writer_last_success_timestamp_seconds` — ошибки и время записи.

Дубликат не увеличивает число записанных строк и histogram скоров. При ошибке БД
writer не подтверждает offset и повторяет запись. Базовые поля сообщения
`transaction_id`, `score`, `fraud_flag`, `model_version` сохранены; добавлены
`us_state`, `merch`, `cat_id`, `amount`, `scored_at`, `produced_at`.

## Проверка смены модели

При работающем потоке запустите ручное переобучение:

```bash
docker compose exec airflow airflow dags trigger retrain_fraud_model \
  --conf '{"force_publish": true}'
docker compose exec airflow airflow dags list-runs -d retrain_fraud_model
```

`force_publish` нужен для демонстрации: без него более слабая модель может законно
остаться кандидатом. Обычное расписание сохраняет проверку champion/challenger.
После успешного DAG:

```bash
cat artifacts/models/latest.txt
docker compose logs fraud_detector | grep 'Загружена модель'
docker compose exec postgres psql -U postgres -d fraud -c \
  'SELECT model_version, count(*) FROM scores GROUP BY 1;'
```

В первом дашборде включена annotation **Новая модель (30 секунд)**: событие
подписано `model_version` и остаётся в истории графика. В момент загрузки
условие активно примерно 30 секунд. Новая версия видна и в PostgreSQL-панели.
Контейнер `fraud_detector` при этом не перезапускается. Если новый файл повреждён,
сервис сохраняет прежнюю модель и увеличивает счётчик ошибки загрузки.

## Проверка алертов

Grafana → Alerting → Alert rules. Два правила автоматически загружены из
`grafana/provisioning/alerting/rules.yml`; вычисление раз в 10 секунд, pending 10 секунд.
Telegram и почта не нужны.

**Нет скоринга более 20 секунд**: `time() - scorer_last_success_timestamp_seconds > 20`.

```bash
docker compose stop simulator
# Подождать около 40–60 секунд: правило должно стать Firing.
docker compose start simulator
# После обработки новых сообщений правило возвращается в Normal.
```

Если в Kafka был большой backlog, сначала дождитесь его обработки. Не останавливайте
сам скорер для этого сценария: так проверяется отсутствие потока при живом сервисе.

**Доля флага фрода выше 10%**: доля по rate за 30 секунд выше 0.10.
Для проверки подайте только реальные строки с target=1; метка не передаётся модели:

```bash
SIMULATOR_MODE=fraud docker compose up -d --no-deps --force-recreate simulator
# Подождать 45–60 секунд, проверить Firing.
SIMULATOR_MODE=normal docker compose up -d --no-deps --force-recreate simulator
# После обновления окна правило возвращается в Normal.
```

Модель может пропускать часть истинных фродов, поэтому речь о доле её флагов.
На поставляемых данных проверяется фактическое срабатывание обоих правил.
При старте до готовности потока возможны временные Pending/NoData.

## Автоматическая проверка

После минуты работы:

```bash
python3 scripts/check_monitoring.py
```

Скрипт проверяет три UP-target, наличие всех дашбордов, непустые PromQL-панели,
SQL-панели с All и выбранными значениями, бизнес-поля в БД и наличие алертов.
Результат — `docs/monitoring-check.json`. Срабатывание алертов и подмена модели
проверяются отдельно описанными выше сценариями.

Тест сохранения прежней модели при повреждённом новом файле:

```bash
docker compose run --rm --no-deps -v "$PWD/tests:/tests:ro" fraud_detector \
  python -m unittest discover -s /tests
```

Команда запускает отдельный временный контейнер с тестом, не перезапуская скорер потока.

Проверка повторной доставки (на время приостанавливает генератор и затем возобновляет):

```bash
python3 scripts/check_duplicates.py
```

Ожидается: `writer_duplicates_total` вырос на 5, `writer_scores_total` и
`writer_score_count` не изменились. Результат — `docs/duplicate-delivery-check.json`.

Результаты проведённого прогона и скриншоты собраны в
[docs/VALIDATION.md](docs/VALIDATION.md). В них есть срабатывание и восстановление
алертов, горячая смена модели и проверка повторной доставки.

## Существующие данные и ДЗ3

`db_writer/monitoring.sql` — идемпотентная миграция: добавляет поля и индексы,
сохраняет старые строки, создаёт read-only пользователя Grafana. При первом старте
её выполняет PostgreSQL после `init.sql`, а при старом томе — writer при запуске.
Старые сообщения без бизнес-полей сохраняются с UNKNOWN, а без `scored_at` не
попадают в временные SQL-графики. Новые сообщения содержат все необходимые поля.

Параметры переобучения сохранены: окно 4 месяца (3 train + 1 test), поставка 3000
строк, история 24 месяца; retrain/supply каждые 5 минут, DQ каждые 10 минут.
Подробности исходного решения — [docs/HW3_README.md](docs/HW3_README.md);
адреса и команды мониторинга из текущего README имеют приоритет.
